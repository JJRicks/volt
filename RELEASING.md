# Releasing Volt

This is the maintainers' process. Contributors don't need it: see [CONTRIBUTING.md](CONTRIBUTING.md).

Release from a reviewed commit on `main`. Keep the repository's existing visibility; publishing a release does not require making it public.

For the first public release, complete [Public release readiness](docs/public-release.md) before changing visibility. The manufacturer-sourced photo is still a placeholder: replacing the current asset alone does not remove copies in older tags, PR refs or release downloads. Decide how to handle those copies before making the existing repository and releases public. Keep permission/provenance records and retain required notices.

The public description and release notes must identify Volt as an independent community project, not affiliated with, endorsed by or sponsored by NAVEE. Use “project release” to distinguish Volt's builds from NAVEE's official software.

1. Increase both `versionName` and `versionCode` in `AndroidManifest.xml`. Keep README.md, README.txt, FEATURES.txt, CHANGELOG.md and the current VERIFICATION.txt section consistent. Add the Model ID of every compatibility report received at volt-reports@jjricks.com to `ModelRegistry.REPORTED`, so Volt stops offering to share one for that model. Diagnostics and map requests read the installed manifest version.
2. Review the final diff and tracked files. Merge the reviewed pull requests into `main` without losing the stacked branch history. Confirm the final commit's checks pass. This merged `main` commit is the release commit. Check it, build it and tag it, and nothing else. If anything merges into `main` after this step, including a translation top-up, start again here with the new commit.
3. Check out the release commit with a clean tree and check the translations with `python3 tools/l10n/ship_check.py --release --aapt required`. No release ships until every shipped language is fully translated (the owner's rule from November 6, 2026). This mode fails if any shipped language still has a key falling back to English, and lists those keys. If it fails, do a translation top-up first and merge it, then go back to step 2. Pull requests run the same check without `--release`, where the fallback share is only a reference line. `VOLT_RELEASE=1 bash build.sh` also runs it and refuses to build when it fails.
4. Explicitly fetch and verify pinned dependencies once with `python3 setup/shizuku-dependencies.py --fetch` (network required only for this step). Then run `bash tests/run.sh`, `python3 tests/owner-capture-guard-test.py`, `python3 tests/capture-owner-test.py`, `python3 tests/hardware-sweep-test.py`, `VOLT_RELEASE=1 bash build.sh` and `bash android-tests/build.sh` with JDK 17 or newer and the documented Android SDK. Review new warnings or failures. The build verifies APK signing and alignment. Without `VOLT_RELEASE=1`, build.sh marks the APK as a development build (versionName `<version>-dev+<commit>`, plus `-dirty` with uncommitted changes), so build the swept candidate with it too; the swept build and the release build must stay content-identical apart from the signing key. `VOLT_RELEASE=1` refuses uncommitted or untracked changes and prints the commit it builds; record that commit.
5. On a disposable emulator, run `python3 android-tests/run-release-sweep.py --adb <sdk adb> --serial emulator-<port> --app dist/volt.apk --runner .local/build/parked-validation/parked-validation.apk --out <evidence dir>`. It runs every registered validation and each mode with checks of its own (compact and expanded layouts, both themes, large text, permission states), and refuses to start if `android-tests/AndroidManifest.xml` registers a class it doesn't cover. Add a step when you add a validation or a mode with new checks. Its `rides-timing` step seeds many rides and gates a cold launch and two Rides opens ("Volt launches instantly", #234 and #240): it fails when the best of two cold starts misses a release budget (1.5 s to the first frame and to the service start command, 1 s for Rides; `run-rides-timing.py` RELEASE_BUDGETS). Bluetooth stays off there, so the service start command, where Volt would begin connecting, stands in for connection start; it is not a connection time. A run that reports a measure as missing (or the validation's -1) fails rather than counting as fast. A miss there means seconds, not load noise: rerun it once with `--only rides-timing` on an idle emulator before treating it as a regression. Rerun a failure with `--only <step>` and record why in VERIFICATION.txt. The closing summary counts gating steps (passed, failed; only these set the exit code) apart from report-only steps (ran, did not finish, skipped), so copy those numbers into VERIFICATION.txt as printed and never count a report-only step as a pass. It refuses phones. Keep physical field-validation limits explicit. Never run destructive emulator setup commands against a phone. Then, with the owner present and the scooter parked beside them (plugged in and charging, to include Test scheduled charging), run `python3 android-tests/run-hardware-sweep.py --adb <sdk adb> --serial <phone serial> --runner <parked-validation.apk> --out <evidence dir> --parked` against the release candidate the owner installed. Build that runner with the same key as the phone's Volt. It refuses emulators, never installs or removes Volt, never writes speed caps, maximum speed or dual motor drive, and runs lock or the PIN state read only with `--include`. Record its report.md outcomes (not its pulled diagnostics, which can hold serials) in VERIFICATION.txt as physical evidence.
6. Build the release APK with `VOLT_RELEASE=1 bash build.sh` and the privately retained release signing identity, from the same commit as the swept build (compare the commit each build printed). Compare its signing certificate with the preceding release APK. Contributor keys are for local builds and cannot update installations signed with the project release key. Do not print, commit or upload keys, passwords, local-build.env, credentials, recordings or phone reports.
7. Confirm that the checked, built and tagged commit are one SHA: the commit checked in step 3, the commit each `VOLT_RELEASE=1` build printed, and `main`'s current commit must all be the release commit from step 2. If any differs, start again at step 2. Then tag that exact `main` commit as `v<version>`. Make a source ZIP from `git archive` of the tag so it contains only tracked source. Upload the signed APK, source ZIP and SHA256SUMS to a draft GitHub release with the matching tag. Never replace an existing tag or published APK with different contents; issue a new version instead.
8. Download the draft assets and verify their checksums and the APK's version, signature and alignment. `aapt dump badging` must show `versionName` exactly as in `AndroidManifest.xml`, with no `-dev`; otherwise the APK came from a build without `VOLT_RELEASE=1`, so rebuild it and replace the draft asset before publishing. Publish the release, then confirm the tag, release assets and `main` revision match. Record what was actually tested in VERIFICATION.txt. With the owner's OK, rebuild `site/` and deploy the homepage so its download line names the new version. Use `site/server/deploy-release.sh` from the release commit, not the old `update.sh`: it runs the live-variant switch after moving `current`, so the variant the owner chose in the Workbench stays live, and it reports which variant that is. If the switch fails or the live variant does not move into the new release, it puts `current` and `live` back where they were without the switch, prints `DEPLOY_FAILED` and exits 1; treat that as a failed deploy. If it prints `DEPLOY_INCOMPLETE`, the rollback did not finish: stop and run the commands it prints, as root, before anything else. `CARD_CONFLICT` means a variant card name already holds other bytes in the append-only card store; nothing changed, so look before deploying again. Then check every manifest file at its served URL: the live variant at `/`, each variant at `/preview/<name>/` (see site/README.md, "Deploy").

The release notes should describe user-visible changes, installation/upgrade behavior and known limitations. A regular GitHub release does not make experimental battery or sensor estimates validated measurements.
