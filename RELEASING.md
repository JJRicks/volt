# Releasing Volt

Release from a reviewed commit on `main`. Keep the repository's existing visibility; publishing a release does not require making it public.

For the first public release, complete [Public release readiness](docs/public-release.md) before changing visibility. The manufacturer-sourced photo is still a placeholder: replacing the current asset alone does not remove copies in older tags, PR refs or release downloads. Decide how to handle those copies before making the existing repository and releases public. Keep permission/provenance records and retain required notices.

The public description and release notes must identify Volt as an independent community project, not affiliated with, endorsed by or sponsored by NAVEE. Use “project release” to distinguish Volt's builds from NAVEE's official software.

1. Increase both `versionName` and `versionCode` in `AndroidManifest.xml`. Keep README.md, README.txt, FEATURES.txt, CHANGELOG.md and the current VERIFICATION.txt section consistent. Add the Model ID of every compatibility report received at volt-reports@jjricks.com to `ModelRegistry.REPORTED`, so Volt stops offering to share one for that model. Diagnostics and map requests read the installed manifest version.
2. Explicitly fetch and verify pinned dependencies once with `python3 setup/shizuku-dependencies.py --fetch` (network required only for this step). Then run `bash tests/run.sh`, `python3 tests/owner-capture-guard-test.py`, `python3 tests/hardware-sweep-test.py`, `bash build.sh` and `bash android-tests/build.sh` with JDK 17 or newer and the documented Android SDK. Review new warnings or failures. The build verifies APK signing and alignment.
3. On a disposable emulator, run `python3 android-tests/run-release-sweep.py --adb <sdk adb> --serial emulator-<port> --app dist/volt.apk --runner .local/build/parked-validation/parked-validation.apk --out <evidence dir>`. It runs every registered validation and each mode with checks of its own (compact and expanded layouts, both themes, large text, permission states), and refuses to start if `android-tests/AndroidManifest.xml` registers a class it doesn't cover. Add a step when you add a validation or a mode with new checks. Rerun a failure with `--only <step>` and record why in VERIFICATION.txt. It refuses phones. Keep physical field-validation limits explicit. Never run destructive emulator setup commands against a phone. Then, with the owner present and the scooter parked beside them (plugged in and charging, to include Test scheduled charging), run `python3 android-tests/run-hardware-sweep.py --adb <sdk adb> --serial <phone serial> --runner <parked-validation.apk> --out <evidence dir> --parked` against the release candidate the owner installed. Build that runner with the same key as the phone's Volt. It refuses emulators, never installs or removes Volt, never writes speed caps, maximum speed or dual motor drive, and runs lock or the PIN state read only with `--include`. Record its report.md outcomes (not its pulled diagnostics, which can hold serials) in VERIFICATION.txt as physical evidence.
4. Build the release APK with the privately retained release signing identity. Compare its signing certificate with the preceding release APK. Contributor keys are for local builds and cannot update installations signed with the project release key. Do not print, commit or upload keys, passwords, local-build.env, credentials, recordings or phone reports.
5. Review the final diff and tracked files. Merge the reviewed pull requests into `main` without losing the stacked branch history. Confirm the final commit's checks pass.
6. Tag that exact `main` commit as `v<version>`. Make a source ZIP from `git archive` of the tag so it contains only tracked source. Upload the signed APK, source ZIP and SHA256SUMS to a draft GitHub release with the matching tag. Never replace an existing tag or published APK with different contents; issue a new version instead.
7. Download the draft assets and verify their checksums and the APK's version, signature and alignment. Publish the release, then confirm the tag, release assets and `main` revision match. Record what was actually tested in VERIFICATION.txt. With the owner's OK, rebuild `site/` and deploy the homepage so its download line names the new version (see site/README.md).

The release notes should describe user-visible changes, installation/upgrade behavior and known limitations. A regular GitHub release does not make experimental battery or sensor estimates validated measurements.
