# Release this scooter (owner release) validation

**Tried on a UT5 MAX (Nov 14, 2026).** The release works on the owner's UT5 MAX, but the scooter doesn't answer with a status: it ends the Bluetooth link instead. Other models remain untested here.

## UT5 MAX results (Nov 14, 2026, Volt 1.13.2-dev+a598f6b)

- The release frame went out over the owner-authenticated link, and about **88 ms** later the scooter ended the link (Android reported a disconnect with status 257 while ready). No 0x50 status reply was seen.
- Before this fix, Volt counted that as "not confirmed" (sent, no answer, link closed), kept the profile, and its usual retry reconnected one second later. A reset scooter takes the first owner key it hears, so that reconnect **claimed the scooter straight back**: it was authenticated with the same key again about 3.2 s after the release. So on the UT5 MAX the release could never finish.
- On a second try Volt was force-stopped about 0.35 s after the tap, before its retry. The NAVEE app then found the scooter as a new one and added it. Afterwards the owner identity from the owner's older backup connected at once: the NAVEE re-link used the same account identity. The odometer was unchanged throughout.

## The official app's unbind, in words

When an owner unbinds a scooter in the NAVEE app, the app first asks NAVEE's server to drop the scooter from the account. Once the server accepts, and while the app still holds the owner-authenticated Bluetooth link, it sends one frame to the scooter: command 0x50 with a single data byte of 1, framed as usual (`55 AA 00 50 01 01 51 FE FD`, where 51 is the low byte of the sum of the six bytes before it). The scooter answers with a status; the app then disconnects. (On the UT5 MAX no status reply was seen: the scooter ended the link itself within about 88 ms, above.) After that the scooter behaves like a new or reset one and accepts a fresh owner binding from anyone nearby.

Volt has no server step. It sends only the scooter frame, so a NAVEE account that lists the scooter keeps listing it.

## Volt's handling

- **Entry.** More → My scooters → Edit scooter → **Release this scooter…**, the filled red main button with a cycle-arrows icon, directly above **Forget this scooter** (now the grey secondary button with its trash icon; the owner's pick, style B, Nov 13), shown only for owner profiles (role 0). A confirmation dialog explains the effect; its button is **Release**. Off the UT5 MAX the dialog also says **Untested here**: Release has the official app's mapping as its only evidence there, as `MainActivity.controlNote` marks other such controls, and the owner's hardware check covers the UT5 MAX alone.
- **Gate.** The tap, the dialog's confirm and the send each recheck. It needs: no ride or charge recording, ride saving, backup, schedule test or pending scooter change (the same `scooterChangeUnavailable` check Forget uses); a ready, authenticated link to that very profile; not simulation; and the mutation gate's release decision: owner, fresh status (cached status never authorises it), parked with a motion report, no compatibility check, guided test or other change in flight, no recording, and a supported product and transport. Only a user tap with value 1 for the `owner_release` feature is admitted.
- **Sending.** The frame is built by `Protocol.ownerRelease()`; the generic `Protocol.frame` still refuses 0x50. It goes out as the admitted mutation through `BleController`, so `MutationGate.mayTransmit` passes only those bytes. 0x50 is a sensitive command: kept out of the event log and raw-frame views. The command log records `owner_release` with its outcome and never a value.
- **Status 0.** Volt disconnects (which cancels any pending reconnect), then at once removes the profile, its maintenance reminders and its model evidence, before anything could reconnect: reconnecting with the same profile would claim the scooter again. Saved rides and charge recordings stay. Toast: "Scooter released".
- **The quick drop counts as released (owner's decision, Nov 14).** When the scooter ends the link itself within **1 second** of the release frame going out (`OwnerRelease.afterDrop`: an Android-reported disconnect, Bluetooth still on, and a status other than 8, a supervision timeout where the link was lost, and 22, a link this phone ended), Volt does exactly what a status-0 reply does: no reconnect is scheduled or left pending, the profile is removed before anything could reconnect, and the same "Scooter released" message shows. It's checked as soon as Android reports the drop, before anything else handles it, so it applies whether Volt is in front or not. A coincidental drop in that second would remove the profile without asking; the owner accepted that small lockout risk (Release needs no key backup, unlike Forget).
- **A refusal or a release never sent changes nothing.** A nonzero status ("The scooter refused the release…") keeps the profile, and Volt stays connected as before. A release refused or cancelled before the frame went out (moving, busy, the link lost while it waited) keeps the profile, and Volt reconnects as usual.
- **Anything else after the send: hold and ask.** No reply within the usual 6.5-second timeout, a drop more than a second after the send, a drop with status 8 or 22, Bluetooth turned off on the phone, Volt pausing out of sight, the owner's Disconnect, switching to another scooter, or the service ending: the scooter may have released, so Volt keeps the profile but **doesn't reconnect to it by itself**. Every automatic path skips it: the retry after a failure, auto-connect when Volt is shown, Bluetooth coming back on, recording and charge-hold reconnects and background connection (they all go through `BleController.connectLast` or `connect`, which refuse a held profile), and Identify model. A link that ends after the release was written reads "change not confirmed", never "cancelled". A sheet then asks, over whatever is in front (now, or when Volt is next in front), until the owner closes it or picks an action: **<name> didn't confirm the release**. It may have released, and if it did, the NAVEE app or another Volt owner key can add it. **Remove from Volt** opens that scooter's own Forget dialog in My scooters, with Forget's rule that a backup holding the owner key must be saved first. **Reconnect** ends the hold and connects; its note says that if the scooter released, reconnecting makes Volt its owner again. Closing the sheet keeps the hold, and an explicit Connect (the Home header, My scooters, Find it nearby or the scan sheet) shows the sheet again instead of connecting. The hold is per scooter: another saved scooter connects normally.
- **The hold is kept on this phone until the owner chooses.** It's saved per scooter in Volt's own storage (`ReleaseHolds`, in a preference file that backups never read, clear or restore), so it outlasts Volt closing, Android ending the service, finishing a key backup (which restarts Volt) and the phone restarting, as well as simulation, Bluetooth off and on, and switching scooters. Only **Reconnect**, forgetting the scooter (**Remove from Volt** ends in Forget) or a confirmed release ends it. A hold left for a scooter that's no longer saved (after a restore, say) is dropped. A backup never carries a hold, and a restore never creates one. The question is saved too: it stays owed until the owner closes the sheet or picks an action, so a sheet lost to a restart or to the screen being recreated (a dark-mode or language change) is shown again. While a scooter is held, Home's connection line says **Release not confirmed · not reconnecting** (or **Release not confirmed** when narrow), and so does its line in My scooters.
- **Known limit:** clearing Volt's storage (Android's Clear storage, or reinstalling) ends the hold along with the profile and its key, so there's nothing left to reconnect with.

## Checks run

- `tests/l10n/OwnerReleaseTest.java` (synthesized fixtures only): the exact frame bytes and checksum; the generic builder's refusal; the gate's conditions (owner, ready, parked, motion report, real scooter, fresh status, idle, product and transport); origins and values other than a user's 1; the radio boundary; the command log's value-free record; and that only status 0 removes the profile.
- `tests/l10n/ReleaseHoldsTest.java`: a sent release that ends unconfirmed holds its scooter on disk; a store built fresh from what was saved (a new process) still holds it, still refuses the retry and still owes the question; only answering clears the question, only Reconnect, Forget or the profile going ends the hold, and nothing else writes. It also checks from the source that every connection path, `close()`, the release timeout, `failed()`, simulation and Forget call into the store, and that the namespace is private to backups.
- `tests/l10n/OwnerReleaseDropTest.java` (synthesized times and codes): a drop up to 1000 ms after the send is released whatever the scooter's status code; a later drop, status 8 or 22, Bluetooth off and anything that isn't a drop are not confirmed and hold; nothing sent is never held; only "not confirmed" holds, and no outcome both removes and holds.
- The hold and its sheet, reasoned and rendered (see the pull request): every automatic reconnect path, the reply and drop racing, the timer after a quick finish, Bluetooth off, the per-scooter hold and Forget's backup rule.
- The full JVM suite, the localization checks and a build; see the pull request for results.
- Emulator renders (a scratch harness, not committed): the Edit scooter dialog and the confirmation, reached through the button, at 412 × 915 dp dark and light, 412 × 915 dp at 130% system text, 344 × 882 dp (Fold cover) dark and at 130% text, and 673 × 841 dp (unfolded Fold). Every button stays on one line with nothing cut off, and a shared scooter's dialog has no Release button. A real release needs a connected, parked scooter, so the harness skipped the readiness check to open the confirmation.

## To test on hardware

On the UT5 MAX: connect as owner, parked, release. Expect the scooter to drop the link at once, "Scooter released", and the scooter gone from My scooters, with no reconnect; then confirm the NAVEE app (or Volt's setup) can add it as a new scooter. Also try a release while moving or as a shared user (both should be refused before sending). On other models, note whether the scooter answers with a status, drops the link, or neither.
